## AI Phase 10 — Customer Outreach Content (✅ done, see DA.34)

**Requested directly by the user**: "on marketing phase, we also need to help our users reach their customers by generating content that they can share." Distinct from AI Phase 6 (Marketing Image Generation) — Phase 6 is store-facing (banners/hero images for the storefront itself); this is customer-outreach content the merchant sends OUT to reach buyers. Not yet built — captured here so the shape and the two decisions already made survive until work actually starts.

**Decisions already made** (via `AskUserQuestion`, both scoped before implementation began — see below for why implementation was paused):
- **Ship scope: Phase A + B together** (text content AND the shareable image, not text-only first).
- **Entry point: inside the AI Assistant chat** — reuses the existing conversational assistant/`configuration_guidance`-style pattern, no new dashboard screen.

**Proposed shape** (not yet built, subject to revision when work starts):
- **Phase A — text**: a new `social_content` intent. Merchant asks (e.g. "write me a post about my new arrivals", "make a WhatsApp message for my sale") → grounded in REAL product name/price/description (resolved against the tenant's real catalog, same resolution pattern as `business_advice`'s specific-product pricing) and REAL business_type/niche (via `getBusinessProfile()`, DA.12) for tone — never invented facts, matching this assistant's whole precision discipline. Generates: a social caption + hashtags, a WhatsApp broadcast/status message, and a short SMS-style blurb, in one Claude call, all three grounded in the same confirmed real facts given in the system prompt.
- **Phase B — shareable image**: reuses the existing Gemini image pipeline (the one DA.16/DA.17 just added real cost tracking and quality-vs-cost judgment for) to render a promotional graphic — styled as a marketing banner/flyer featuring the real product name/price as text elements, NOT a photorealistic depiction claiming to BE the real product (same reasoning `AI_FEATURES_PLAN.md` already applied to starter-pack sales-promotion banners: a stylized promotional graphic doesn't misrepresent the product the way a fabricated "photo" of it would). Real, unresolved design question flagged for when this is built: image generation takes ~10-11 real observed seconds (DA.17's live timing) — too slow for a single synchronous assistant-chat turn — so this likely needs the SAME suggest-then-confirm two-turn hand-off already built for category creation (DA.12: propose, then a following "yes" triggers the real (slower) action), reused here for "want me to make a shareable graphic too?" rather than invented as a new mechanism.
- **New AiFeature/usage tracking**: a new Gemini call site distinct from `starter_pack_content`/`starter_pack_image` (DA.16) — needs its own `AiFeature` identifiers (e.g. `social_content_text`, `social_content_image`) so the AI Usage page (DA.15) can break it out separately from onboarding costs.

**Why this is documented but not started**: the user asked to prioritize AI Phase 8.2 (Usage-vs-limit upgrade nudges) first, right after this was scoped — captured here rather than left only in chat history so the scoping work (and the two AskUserQuestion decisions) isn't lost. A partial, inert edit toward this (adding `social_content` to `SUPPORTED_INTENTS` with no handler behind it) was made and then explicitly reverted before switching tasks, to avoid leaving the shared assistant module in a half-built state — `git diff`/`tsc` clean, no trace of the paused work in the code itself, only here.

## UI — Onboarding AI Chat (new, cross-platform, own plan doc)

Full detail in [`ONBOARDING_AI_CHAT_PLAN.md`](./ONBOARDING_AI_CHAT_PLAN.md) — **that doc's "Current state" section is now known-inaccurate, see the OC.2 correction below; treat this tracker as authoritative over it for scope.**

**⚠️ Scope correction (found while starting OC.2):** the plan doc's premise — that `dashboard/onboarding/starter-pack/page.tsx` is a real merchant-facing form this chat replaces — was wrong. On inspection that page is an internal generation-testing harness (`StarterPackTestingPage`, hardcoded defaults, dev-only toggles like `includeGeminiCall`). The **real** production flow: `/register` is a single monolithic form (email/password/subdomain/phone/referrer + a `businessType` dropdown) that POSTs once to `POST /api/tenants/register`, a ~2600-line route that creates the account **and** triggers starter-pack generation server-side in the same call, with its own background-job/fallback machinery. There is no separate post-registration screen today — the user lands straight in the dashboard after a cross-origin login redirect (`data.loginUrl`). There's no `niche` field anywhere in the real form; currency is auto-detected, not chosen.

Given that, "replace the form" had no real target — the only real candidate was one dropdown field inside a live, revenue-critical route serving 182 real tenants. **Presented this to the user directly** (via AskUserQuestion) rather than guessing; they chose **"Additive post-registration step"**: leave `/register` and `POST /api/tenants/register` completely untouched, add the chat as a new, separately-reachable page that enriches the business context already collected, rather than being the sole intake or replacing anything. Automatically wiring it into the post-registration redirect was deliberately **not** done in this pass — that redirect goes through a cross-origin login handoff (`loginUrl`) whose auto-auth behavior wasn't verified, and changing it blind on a live signup path was judged too risky; it's a clearly-flagged follow-up, not silently dropped.
